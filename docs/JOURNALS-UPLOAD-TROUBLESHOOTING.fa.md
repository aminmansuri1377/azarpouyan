# اصلاح توقف آپلود گاهنامه

این patch تکمیلی روی نسخه‌ای اعمال می‌شود که هر سه patch قبلی (گاهنامه، سقف ۱۵۰ مگابایت و نوار پیشرفت) را دارد. وابستگی یا migration جدید لازم نیست.

## چرا نوار ۱۰۰٪ است ولی درخواست pending می‌ماند؟

نوار، پیشرفت مرورگر تا برنامه Next.js را نشان می‌دهد. در localhost این مرحله می‌تواند سریع تمام شود؛ پس از آن، رایانه‌ای که `npm run dev` را اجرا می‌کند باید فایل را از اینترنت به لیارا بفرستد. ۱۰۰٪ به‌تنهایی به معنی ذخیره در باکت نیست. از screenshot نمی‌توان علت قطعی کندی یا توقف ارتباط را تشخیص داد.

## تغییرات

- فایل‌های بیشتر از ۵ MiB با API چندبخشی S3، در قطعات ۵ MiB ارسال می‌شوند. هر درخواست حداکثر دو بار تلاش دارد و هر قطعه با Content-MD5 بررسی می‌شود. checksum اختیاری مخصوص AWS درخواست نمی‌شود.
- مهلت اتصال ۱۰ ثانیه، بی‌فعالیتی سوکت ۶۰ ثانیه، هر درخواست ۳ دقیقه و مجموع ارسال هر فایل ۲۰ دقیقه است. این اعداد حداکثر انتظارند؛ خطاهای معمول زودتر پاسخ می‌گیرند. پاک‌سازی هر فایل/آپلود ناتمام نیز مهلت ۱۵ ثانیه‌ای دارد.
- در صورت شکست آپلود چندبخشی، AbortMultipartUpload ارسال می‌شود. اگر پاک‌سازی به علت قطع شبکه شکست بخورد، شناسه آپلود ناتمام در لاگ ثبت می‌شود تا در فضای ابری بررسی شود.
- تصویر جلد کوچک قبل از PDF ارسال می‌شود تا خطای دسترسی زودتر مشخص شود. در صورت شکست، پاک‌سازی فایل‌های جدید همچنان انجام می‌شود.
- کپی‌های اضافی کل بدنه درخواست حذف شده‌اند و PDF برای ارسال به قطعات کوچک خوانده می‌شود. parser فرم همچنان کل فایل ورودی را در حافظه نگه می‌دارد؛ این روش آپلود مستقیم مرورگر به S3 یا آپلود کاملاً بدون بافر نیست.
- تنظیمات اتصال مخصوص گاهنامه است؛ `lib/s3.ts` و آپلود تصاویر سایر بخش‌ها تغییر نکرده‌اند. از همان متغیرهای `S3_*` موجود استفاده می‌شود.
- درخواست مرورگر پس از ۳۰ دقیقه انتظار خاتمه می‌یابد و اعلام می‌کند که نتیجه نامشخص است؛ قبل از ارسال مجدد، فهرست و لاگ را بررسی کنید تا رکورد تکراری ثبت نشود.

## اجرا

از ریشه پروژه:

```bash
git apply --check azarpouyan-journals-upload-fix.patch
git apply azarpouyan-journals-upload-fix.patch
```

در localhost، فرایند قبلی `npm run dev` را با Ctrl+C متوقف کنید، سپس دوباره `npm run dev` را اجرا کنید و صفحه را تازه کنید. درخواست قدیمیِ pending را ادامه ندهید.

برای production، `npm run build` و سپس انتشار با روال فعلی پروژه لازم است.

## پیدا کردن مرحله توقف

ترمینالی را که Next.js در آن اجراست باز نگه دارید؛ در production لاگ برنامه را ببینید. گزارش‌های جدید این ترتیب را دارند:

| پیام | معنا |
| --- | --- |
| `[journal] authorized` | درخواست وارد سرور شده و نشست ادمین تأیید شده است |
| `[journal] form received` | دریافت و پردازش بدنه تمام شده است |
| `[journal-storage] start` | ارسال یک فایل به لیارا شروع شده است |
| `[journal-storage] part uploaded` | یک قطعه در لیارا پذیرفته شده است؛ درصد انتقال سمت سرور در لاگ آمده است |
| `[journal-storage] complete` | ذخیره فایل توسط سرویس تأیید شده است |
| `[journal] files stored; saving record` یا `updating record` | فایل‌ها تمام شده‌اند و نوبت ثبت دیتابیس است |
| `[journal-storage] failed` | مرحله، نام/کد خطا و وضعیت HTTP مشخص می‌شوند |

اگر `AccessDenied` یا 403 دیدید، کلیدهای دسترسی، نام باکت و مجوز نوشتن/آپلود چندبخشی را بررسی کنید. اگر `ENOTFOUND` یا `EAI_AGAIN` بود، endpoint و DNS محیط اجرای Next.js را بررسی کنید. `TimeoutError`، `AbortError` یا خطای اتصال به معنی مشکل/کندی ارتباط یا پایان مهلت است و به‌تنهایی مشکل خاصی مثل VPN را ثابت نمی‌کند. `SignatureDoesNotMatch` نیازمند بررسی کلیدها، region، endpoint و ساعت رایانه است.

مقادیر S3 باید در محیط همان فرایند Next.js موجود باشند. تنظیمات پنل لیارا خودکار به localhost منتقل نمی‌شوند. چون بخش‌های دیگر پروژه هنوز از `lib/s3.ts` اصلی استفاده می‌کنند، قالب فعلی `S3_ENDPOINT` بدون `https://` را حفظ کنید.

اگر هنوز مشکل داشتید، آخرین پیام‌های `[journal]` و `[journal-storage]` را همراه خطای نمایش‌داده‌شده در فرم ارسال کنید. فایل `.env` یا کلیدهای دسترسی را ارسال نکنید.

## بررسی

TypeScript، ESLint و build production بررسی شده‌اند. با SDK واقعی و HTTP fixture محلی، فایل ۱۰۵ MiB در ۲۱ قطعه ارسال و تکمیل شد. پاسخ 403، لغو آپلود ناتمام، درخواست بی‌پاسخ با مهلت کوتاه‌شده در آزمون، حذف فایل و محدودیت حجم نیز بررسی شدند. این آزمون‌ها اتصال واقعی به باکت شما یا اینترنت رایانه شما را تأیید نمی‌کنند.
