# گاهنامه با tRPC و آپلود مستقیم به لیارا

این راهنما جایگزین بخش‌های آپلود راهنماهای قبلی است. patch تکمیلی روی نسخه‌ای اعمال می‌شود که هر چهار patch قبلی را دارد: گاهنامه، سقف ۱۵۰ مگابایت، نوار پیشرفت و اصلاحیه آپلود چندبخشی. جدول و اطلاعات گاهنامه‌های موجود حفظ می‌شوند؛ migration یا پکیج جدید لازم نیست.

## علت تغییر

در نسخه قبلی، فایل ابتدا به localhost/Next.js می‌رسید و سپس همان سرور فایل بزرگ را به لیارا می‌فرستاد. نوار ۱۰۰٪ پایان مرحله اول بود. خطای timeout فقط نشان می‌داد ارتباط سرور با فضای ابری تمام نشده است؛ از این پیام به‌تنهایی نمی‌توان ایراد endpoint، DNS، اینترنت یا تنظیمات محلی را قطعی دانست.

در نسخه فعلی، روتر مستقل `server/trpc/routers/journal.ts` با `router`، `adminProcedure` و `publicProcedure` موجود پروژه ساخته و به `appRouter` متصل شده است:

| procedure | دسترسی و وظیفه |
| --- | --- |
| `journal.getAll` | ادمین؛ فهرست پنل |
| `journal.getPublished` | عمومی؛ فقط شماره‌های منتشرشده |
| `journal.prepareUpload` | ادمین؛ ساخت لینک‌های امضاشده و رسید محدود به همان گاهنامه |
| `journal.create` | ادمین؛ بررسی فایل‌ها و ثبت رکورد |
| `journal.update` | ادمین؛ بررسی نسخه و فایل‌های جایگزین، به‌روزرسانی رکورد |
| `journal.delete` | ادمین؛ حذف رکورد و فایل‌های آن |
| `journal.getDownloadUrl` | لینک دانلود؛ پیش‌نویس فقط برای ادمین |
| `journal.checkStorage` | ادمین؛ آزمون پاسخ شبکه endpoint از سرور |

CRUD و فهرست REST قبلی حذف شده‌اند. پنل و صفحه درباره ما از کلاینت tRPC پروژه استفاده می‌کنند. مسیر قدیمی دانلود صرفاً برای لینک‌های قبلی باقی مانده و به همان procedure در روتر tRPC واگذار شده است. دانلودهای رابط جدید هم از tRPC لینک می‌گیرند.

فقط انتقال باینری فایل یک `PUT` مستقیم از مرورگر به فضای ابری است؛ فایل در JSON/base64 درخواست‌های tRPC قرار نمی‌گیرد. این الگو برای فایل بزرگ، عبور دوباره از سرور و نگه‌داری PDF در حافظه Next.js را حذف می‌کند. سقف PDF همچنان ۱۵۰ MiB و جلد ۵ MiB است. جلد در این نسخه با همان قالب JPG/PNG/WebP ذخیره می‌شود و دیگر به WebP تبدیل نمی‌شود؛ سرور نوع واقعی و ابعاد آن را بررسی می‌کند.

## اعمال patch

در ریشه پروژه:

```bash
git apply --check azarpouyan-journals-trpc-direct-upload.patch
git apply azarpouyan-journals-trpc-direct-upload.patch
```

فرایند قبلی `npm run dev` را متوقف کنید. تنظیم CORS بخش بعد را انجام دهید و سپس `npm run dev` را اجرا و صفحه پنل را تازه کنید. برای production، `npm run build` و انتشار با روال فعلی لازم است. اگر هنوز کش قدیمی مرورگر فعال است، صفحه را کامل refresh کنید.

## تنظیم CORS باکت ـ لازم برای آپلود از مرورگر

سرور باید از متغیرهای فعلی `S3_ENDPOINT`، `S3_BUCKET`، `S3_REGION`، `S3_ACCESS_KEY` و `S3_SECRET_KEY` استفاده کند. `ADMIN_SESSION_SECRET` فعلی برای رسید آپلود استفاده می‌شود. در localhost متغیرها باید در محیط همان Next.js (مثلاً `.env.local`) موجود باشند؛ تنظیم پنل لیارا خودکار به رایانه شما منتقل نمی‌شود.

از endpoint بخش «دسترسی با SDK» باکت استفاده کنید، نه URL یک تصویر یا دامنه سایت. قالب موجود پروژه برای `S3_ENDPOINT` را بدون `https://` نگه دارید، چون مسیر تصاویر قدیمی همچنان از `lib/s3.ts` اصلی استفاده می‌کند.

برای اجازه دادن به localhost:

```bash
npx tsx scripts/configure-journal-cors.ts --origins http://localhost:3000
```

برای دامنه واقعی، مقدار نمونه را با مبدأ واقعی سایت جایگزین کنید:

```bash
npx tsx scripts/configure-journal-cors.ts --origins http://localhost:3000,https://YOUR-DOMAIN
```

این اسکریپت متغیرها را مانند Next.js بارگذاری می‌کند، CORS فعلی را می‌خواند، قانون مشخص `azarpouyan-journal-upload` را اضافه/به‌روز می‌کند و قوانین دیگر را حفظ می‌کند. مبدأها باید دقیقاً شامل پروتکل و پورت صحیح، بدون مسیر یا اسلش انتهایی باشند. استفاده از `127.0.0.1` به‌جای `localhost` نیازمند اضافه‌کردن همان مبدأ است.

کلید اجرای این اسکریپت باید مجوز `GetBucketCors` و `PutBucketCors` داشته باشد. کلید محدود به فایل‌ها ممکن است این مجوز را نداشته باشد؛ در آن صورت قانون معادل را با کلید مدیریتی باکت یا ابزار مدیریت فضای ابری تنظیم کنید. نیازی به عمومی‌کردن باکت نیست. CORS جایگزین امضای معتبر و مجوز فایل نیست.

قانون موردنیاز، برای اضافه‌کردن به قوانین فعلی:

```json
{
  "ID": "azarpouyan-journal-upload",
  "AllowedOrigins": ["http://localhost:3000", "https://YOUR-DOMAIN"],
  "AllowedMethods": ["PUT"],
  "AllowedHeaders": ["content-type"],
  "MaxAgeSeconds": 3600
}
```

اسکریپت CORS را روی باکت شما در این محیط اجرا نکرده‌ایم. اگر خود اسکریپت timeout بدهد، هنوز ارتباط رایانه/محیط اجرا به endpoint برقرار نیست؛ افزایش حجم یا تغییر tRPC چنین قطعی شبکه‌ای را حل نمی‌کند.

## رفتار آپلود و پیگیری خطا

1. «ذخیره» لینک‌ها را از `journal.prepareUpload` می‌گیرد؛ امضای لینک محلی است و فایل بزرگ از tRPC عبور نمی‌کند.
2. مرورگر فایل‌ها را مستقیماً به لیارا می‌فرستد؛ درصد نوار، مجموع بایت‌های تصویر و PDF در این ارسال مستقیم است.
3. پس از پاسخ موفق لیارا، پیام بررسی و ثبت نمایش داده می‌شود. سرور با `HeadObject` اندازه و نوع را بررسی می‌کند؛ فقط ۵ بایت ابتدای PDF و تصویر حداکثر ۵ MiB را برای اعتبارسنجی می‌خواند، سپس رکورد را ثبت می‌کند.
4. پیش‌نویس و انتشار همان رفتار قبلی را دارند. ویرایش هم‌زمان با کنترل `updatedAt` رد می‌شود.

دکمه «بررسی اتصال سرور به لیارا» باید پاسخ endpoint را نشان دهد. دریافت HTTP 403 از ریشه endpoint در این آزمون صرفاً نشانه دریافت پاسخ HTTP است؛ صحت کلید، اجازه باکت یا CORS را ثابت نمی‌کند.

| محل خطا | اقدام |
| --- | --- |
| `network-check` در tRPC | endpoint، DNS و اتصال محیط اجرای Next.js را بررسی کنید |
| `PUT` مستقیم در Network مرورگر، خطای CORS | مبدأ دقیق صفحه و قانون PUT باکت را بررسی کنید |
| `PUT` با پاسخ 403 | کلید، مجوز نوشتن، ساعت سیستم و انقضای لینک را بررسی کنید |
| `verify-pdf` یا `verify-cover` | سرور باید به S3 برای HeadObject/GetObject دسترسی داشته باشد؛ کد خطا در پیام آمده است |
| فایل در لیارا هست ولی ثبت دیتابیس شکست خورده | تا وقتی فرم باز است «ذخیره» را دوباره بزنید؛ فایل‌های موفق دوباره ارسال نمی‌شوند |

این تغییر، مسیر ارسال بزرگ از localhost به لیارا را حذف می‌کند؛ اما اگر سرور حتی نتواند چند بایت از endpoint بخواند، مشکل شبکه/تنظیمات واقعی همچنان باید برطرف شود. خطای بعدی را همراه نام procedure، مرحله، HTTP status و کد خطا ارسال کنید؛ کلیدها، `.env` و لینک امضاشده را ارسال نکنید.

## فایل‌های ناتمام و تلاش مجدد

رسیدهای آپلود به همان گاهنامه و نوع فایل محدودند و با secret سرور امضا شده‌اند. ایجاد مجدد همان شناسه و همان فایل‌ها پس از گم‌شدن پاسخ، رکورد تکراری نمی‌سازد. رابط تا زمانی که صفحه باز و فایل‌ها یکسان هستند، نتیجه ارسال موفق را نگه می‌دارد تا خطای مرحله ثبت بدون تکرار آپلود قابل تلاش باشد. پس از انقضای لینک یا تعویض فایل، لینک جدید گرفته می‌شود.

فایل‌های جدید در صورت شکست مبهم شبکه/دیتابیس خودکار پاک نمی‌شوند؛ ممکن است رکورد ثبت شده باشد ولی پاسخ به مرورگر نرسیده باشد. بستن فرم، تعویض فایل یا لغو کار قبل از ثبت می‌تواند فایل بی‌مرجع در `journals/` باقی بگذارد. برای پاک‌سازی، فقط فایل‌هایی را حذف کنید که `pdfKey` یا `coverKey` هیچ رکوردی به آن‌ها اشاره نمی‌کند. روی کل مسیر گاهنامه قانون حذف زمانی نگذارید. فایل قدیمی پس از تعویض موفق یا حذف گاهنامه پاک می‌شود؛ شکست پاک‌سازی در لاگ گزارش می‌شود.

## بررسی انجام‌شده

- TypeScript، ESLint فایل‌های تغییرکرده و build production.
- آزمون با tRPC caller واقعی و SDK واقعی، دیتابیس شبیه‌سازی‌شده و endpoint HTTP محلی: ارسال مستقیم PDF با حجم ۱۰۵ MiB، بررسی رمزنگاری امضای PUT و هدرهای آن، دریافت تنها ۵ بایت PDF برای اعتبارسنجی، کنترل دسترسی، رسید دستکاری‌شده/متعلق به رکورد دیگر، تلاش مجدد، تعارض ویرایش، پنهان‌بودن پیش‌نویس، دانلود و پاک‌سازی.
- اعمال patch روی وضعیت پس از چهار patch قبلی.

آزمون با باکت واقعی شما و تنظیمات CORS مرورگر روی آن انجام نشده است. این مرحله پس از تنظیم CORS و اتصال محیط شما باید انجام شود.
