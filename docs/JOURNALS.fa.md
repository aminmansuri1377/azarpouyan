# مدیریت گاهنامه آذرپویان

این تغییر بر مبنای commit `e82c2716f2bb4c3d369a522392b0a472009a6c22` از شاخه `main` آماده شده است.

## روش انتخاب‌شده

- جدول مستقل `Journal` در PostgreSQL: عنوان، توضیحات، کلید تصویر، کلید PDF، حجم PDF، وضعیت انتشار، ترتیب نمایش و تاریخ‌ها.
- فایل‌ها در همان باکت فعلی لیارا و زیر مسیرهای `journals/pdf/` و `journals/cover/` ذخیره می‌شوند. فایل باینری وارد دیتابیس یا دیسک برنامه نمی‌شود.
- تصویر با `sharp` موجود پروژه به WebP با عرض حداکثر ۱۶۰۰ تبدیل و از مسیر تصویر موجود پروژه نمایش داده می‌شود.
- PDF هنگام دانلود از مسیر `/api/journals/:id/download` یک پاسخ 302 به لینک امضاشده ۵ دقیقه‌ای لیارا می‌گیرد. هدر `Content-Disposition: attachment` همراه نام فارسی فایل، دانلود را درخواست می‌کند. ذخیره خودکار یا نمایش پنجره انتخاب مسیر به تنظیمات مرورگر هم بستگی دارد.
- داده PDF هنگام دانلود از سرور Next.js عبور نمی‌کند. بنابراین بار RAM و ترافیک دانلود روی سرور برنامه اضافه نمی‌شود؛ هزینه فضای ذخیره‌سازی و ترافیک لیارا طبق پلن فعلی شما باقی است.
- برای آپلود کم‌تکرارِ ادمین، multipart از سرور برنامه به همان S3 ارسال می‌شود. این انتخاب تنظیمات CORS یا سرویس جدید لازم ندارد. سقف PDF برابر ۱۵۰ MiB و تصویر ۵ MiB است؛ سقف کل درخواست ۱۵۶ MiB است. برای فایل‌های بزرگ‌تر یا آپلود پرتعداد، آپلود مستقیم امضاشده و تنظیم CORS مرحله بعدی خواهد بود.
- تنها وابستگی اضافه‌شده `@aws-sdk/s3-request-presigner` است؛ Next.js، Tailwind، Prisma، احراز هویت، آپلود تصاویر سایر بخش‌ها و تنظیمات فعلی لیارا تغییر نمی‌کنند.

مستندات مرجع:
- https://developers.liara.ir/pages/object-storage
- https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/Package/-aws-sdk-s3-request-presigner/

## اعمال patch و انتشار

ابتدا از دیتابیس production نسخه پشتیبان تهیه کنید و تغییرات محلی خود را commit یا stash کنید. دستورها در ریشه پروژه اجرا شوند:

```bash
git apply --check /path/to/azarpouyan-journals.patch
git apply /path/to/azarpouyan-journals.patch
npm ci
npx prisma generate
npx prisma migrate status
npx prisma migrate deploy
npm run build
```

`DATABASE_URL` باید در محیط اجرای migration به دیتابیس موردنظر اشاره کند. در production، migration جدید را **پیش از در دسترس قرار گرفتن نسخه جدید برنامه** اجرا کنید؛ برای نمونه از محیط انتشار یا کنسول دارای دسترسی به دیتابیس لیارا. سپس با روال فعلی پروژه deploy کنید. build به‌تنهایی migration را اجرا نمی‌کند.

اگر `migrate status` نشان داد migration اولیه پروژه نیز pending است، درحالی‌که جدول‌ها از قبل وجود دارند، ابتدا وضعیت migrationهای قبلی را بررسی و baseline صحیح را برقرار کنید؛ دستورهای `migrate reset` یا `migrate dev` را روی production اجرا نکنید. migration این قابلیت تنها جدول جدید و ایندکس آن را می‌سازد و داده‌های قبلی را تغییر نمی‌دهد.

اگر `git apply --check` خطا داد، نسخه محلی شما با مبنای patch تفاوت دارد؛ از اعمال اجباری یا `--reject` بدون بررسی خودداری کنید.

## تنظیمات لیارا

از متغیرهای فعلی `S3_REGION`، `S3_ENDPOINT`، `S3_ACCESS_KEY`، `S3_SECRET_KEY` و `S3_BUCKET` استفاده می‌شود. متغیر جدید لازم نیست. مطابق `lib/s3.ts` فعلی، مقدار `S3_ENDPOINT` بدون `https://` است.

کلید فعلی باید مجوز خواندن، نوشتن و حذف اشیا در باکت را داشته باشد. دسترسی دانلود به endpoint لیارا از مرورگر کاربران نیز لازم است. هیچ تغییری در public/private بودن باکت موجود ندهید؛ تصاویر دیگر سایت از همین باکت استفاده می‌کنند. مجوز یا کلید S3 به مرورگر ارسال نمی‌شود، فقط لینک موقت یک فایل ارسال می‌شود.

محدودیت بدنه درخواست در هر پراکسی سفارشی جلوی برنامه باید حداقل ۱۵۶ MiB باشد. هنگام آپلود تب را تا اعلام موفقیت نبندید.

## استفاده در پنل

به `/panel/journals` بروید یا از منوی «گاهنامه‌ها» وارد شوید:

1. عنوان، توضیحات، تصویر و PDF را ثبت کنید.
2. برای نمایش عمومی، گزینه «انتشار در سایت» را فعال و ذخیره کنید. مقدار پیش‌فرض، پیش‌نویس است.
3. شماره‌های جدید با ترتیب یکسان، زیر شماره‌های قبلی قرار می‌گیرند. عدد ترتیب کوچک‌تر، بالاتر نمایش داده می‌شود.
4. در ویرایش، اگر فایل جدید انتخاب نکنید فایل قبلی باقی می‌ماند. پس از جایگزینی موفق، فایل قدیمی از فضای ابری حذف می‌شود.
5. حذف گاهنامه پس از تأیید، رکورد و فایل‌های مربوط به همان شماره را حذف می‌کند. برای مخفی‌کردن بدون حذف فایل، انتشار را غیرفعال کنید.

کارت ثابت قبلی به داده دیتابیس تبدیل شده است. چون فایل PDF شماره اول در مخزن موجود نیست، داده ساختگی یا لینک دانلود نامعتبر seed نشده است. پس از انتشار نسخه جدید، شماره اول را از پنل ثبت کنید؛ تا آن زمان پیام «گاهنامه‌ای هنوز منتشر نشده است» نمایش داده می‌شود. توضیحات و عنوان فعلی را می‌توانید برای اولین رکورد استفاده کنید.

متن‌ها، مانند بخش فعلی گاهنامه، فارسی و بین زبان‌های سایت مشترک هستند. جدول ترجمه یا تغییر سازوکار زبان‌ها اضافه نشده است.

## رفتار خطا و نگهداری

- ایجاد، ویرایش و حذف فقط با همان نشست معتبر ادمین پروژه انجام می‌شود. نوشتن از مبدأ دیگر رد می‌شود.
- حجم و امضای ابتدایی `%PDF-` فایل PDF بررسی می‌شود؛ تصویر واقعاً decode و تبدیل می‌شود. این بررسی PDF به معنی اسکن ویروس یا تحلیل کامل محتوای آن نیست.
- تا قبل از ذخیره موفق رکورد، فایل قبلی حفظ می‌شود. اگر آپلود یا ذخیره شکست بخورد، پاک‌سازی فایل‌های تازه تلاش می‌شود.
- اگر حذف یک فایل از S3 شکست بخورد، عملیات پایگاه داده برگشت داده نمی‌شود؛ کلید فایل با پیام `Journal orphan file; remove manually:` در لاگ سرور ثبت می‌شود و باید دستی پاک شود. خطای هم‌زمانی نیز با پاسخ 409 از بازنویسی عملیات در حال اجرا جلوگیری می‌کند.
- توقف ناگهانی فرایند بین آپلود و ثبت دیتابیس می‌تواند فایل بی‌مرجع باقی بگذارد. در صورت وقوع، تنها فایل‌هایی را حذف کنید که `pdfKey` یا `coverKey` هیچ رکوردی به آن‌ها اشاره نمی‌کند؛ برای کل مسیر `journals/` قانون حذف خودکار زمانی نگذارید.
- «پیش‌نویس» به معنی پنهان‌شدن در فهرست عمومی و مسدودشدن مسیر دانلود عمومی گاهنامه است، نه محرمانگی فایل در یک باکت عمومی. مسیر عمومی تصاویر موجود پروژه نیز تغییر نکرده است. برای فایل‌های محرمانه باید باکت و مسیر خواندن اختصاصی و خصوصی طراحی شود. لینک دانلود صادرشده تا انقضا می‌تواند معتبر بماند.

## بررسی انجام‌شده

- `npm run build`: موفق، همراه تولید Prisma Client، TypeScript و خروجی production.
- `npx tsc --noEmit`: موفق پس از تولید typeهای Next.js.
- ESLint روی فایل‌های منطق و رابط جدید/تغییریافته گاهنامه: موفق.
- `prisma validate`: موفق.
- آزمون محلی handlerها با دیتابیس و S3 شبیه‌سازی‌شده: احراز هویت، رد درخواست cross-origin، محدودیت حجم، PDF و تصویر نامعتبر، ایجاد/ویرایش/حذف، حفظ فایل قبلی، پاک‌سازی پس از جایگزینی/شکست/تعارض، پنهان‌بودن پیش‌نویس و هدر دانلود امضاشده.
- `git apply --check` و اعمال روی checkout تمیز commit مبنا بررسی شده است.

اتصال واقعی به دیتابیس و باکت production شما در این محیط انجام نشده است. پس از deploy، یک شماره پیش‌نویس آزمایشی بسازید، دانلود از پنل را بررسی کنید، آن را منتشر و دانلود در حالت ناشناس مرورگر را امتحان کنید؛ سپس تعویض PDF و غیرفعال‌کردن انتشار را بررسی کنید.

## اصلاحیه حجم PDF

این اصلاحیه روی patch قبلی نصب می‌شود. سقف PDF در فرم و سرور از یک فایل مشترک `lib/journal-upload-limits.ts` خوانده می‌شود و برابر ۱۵۰ MiB است؛ فایل ۱۰۵ مگابایتی در این محدوده قرار دارد. سقف کل درخواست ۱۵۶ MiB و سقف جلد همچنان ۵ MiB است. migration یا نصب وابستگی جدید لازم نیست؛ پس از اعمال patch، build و deploy مجدد لازم است.

آپلود همچنان با روش نسخه قبلی از سرور انجام می‌شود و پردازش multipart چند کپی از فایل در حافظه می‌سازد؛ RAM مصرفی می‌تواند چند برابر اندازه PDF باشد. آپلود واقعی به لیارای شما در این محیط آزمایش نشده است. اگر پاسخ 413 از پراکسی دریافت شود، سقف همان پراکسی باید دست‌کم ۱۵۶ MiB باشد؛ اگر فرایند با کمبود حافظه متوقف شود، نیاز به افزایش RAM یا تغییر به آپلود مستقیم S3 است.
